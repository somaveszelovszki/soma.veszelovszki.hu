babocar

The hardware and software for a self-driving model car: circuit boards, 3D-printed parts, real-time firmware spread across several microcontrollers, and a web dashboard for testing and debugging. Every part of it was designed and built by hand.

Overview

babocar is a complete, self-built autonomous model car. It can follow guide lines on the floor, drive predefined routes, find its way through a line maze, and run a high-speed race track that includes overtaking and lane changes. It set the all-time lap record at RobonAUT, the autonomous model car race held at the Budapest University of Technology and Economics.

The project covers the whole stack:

  • Circuit design: schematics and PCB layouts in Altium Designer for the control panel, motor controller, line detectors, distance sensor adapters and an RS422 adapter.
  • Mechanical design: 3D-printed parts modelled in SketchUp and Autodesk Fusion 360.
  • Embedded firmware: separate C++ projects for each microcontroller, built on FreeRTOS and a shared, unit-tested utility library.
  • Tooling: a monitoring and debugging application that runs on a Raspberry Pi on the car.

Distributed architecture

The system is split across several circuits and microcontrollers that communicate over a CAN bus. Each unit has a single responsibility, so it can be developed, tested and replaced on its own.

Motor controller

The low-level motor controller ramps the drive motor's speed and the front and rear steering servos to their target positions. It reads a speed sensor and an RC receiver, and broadcasts the car's actual speed and steering to the other units.

Control panel

The high-level control panel drives the car along a target trajectory by sending speed and steering commands to the motor controller. Its FreeRTOS tasks handle control, line detection, distance sensing, debugging and the two race programs. The trajectory can come from:

  • a predefined route
  • a higher-level trajectory planner
  • guide lines on the floor, picked up by dedicated detector boards at the front and the back

For the maze stage, the firmware models the course as a graph and plans routes through it. On the race track, it runs a set of maneuvers: lane changes, overtaking and turning around.

Line detectors and distance sensors

The front and rear line detectors filter raw sensor readings and work out line positions and line patterns. They have unit tests and benchmarks. Separate time-of-flight sensor adapters report the distance to obstacles ahead of and behind the car.

Monitoring application

The monitor app makes testing and debugging easier with a clear interface for viewing and changing the car's key parameters while it drives. It runs on the Raspberry Pi on the car, as a set of Node.js services that communicate through an MQTT broker:

  • a serial connector that passes messages between the car's control unit and the broker
  • a React web client that shows the car's position, speed, map and logs, and lets you edit firmware parameters such as controller gains
  • a feed recorder and a readback connector, so recorded test drives can be replayed later
  • a simulator that stands in for a moving car while the UI is being developed

Engineering practices

Hardware-independent firmware logic is built and unit-tested on the development machine. A single script builds the tests for the shared library and every firmware project, using the build platform as the target. Hardware access goes through the micro-utils abstraction layer, which has FreeRTOS, STM32 HAL and mock implementations. That's what makes it possible to test control logic without a car.

The repository also includes my MSc thesis, Development of Navigation Methods in Dynamic Environment for an Intelligent Model Car. It covers a mapping method that separates static obstacles from moving ones, and local obstacle avoidance built on top of it. Read the thesis (PDF) ↗
